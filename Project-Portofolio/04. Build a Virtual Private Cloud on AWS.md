### What is Amazon VPC?

`Amazon VPC` is logically isolated virtual network within the AWS cloud that is dedicated to your AWS account. it's like having your own private section of the internet within AWS. and it is useful because : 

1. You can define the _ip address_ space for your `VPC` using `CIDR Blocks`. 
2. You can divide your VPC into one or more subnets, which are like smaller, isolated sections within your private network. You can designate these as public (_accessible from the internet_) or private (_isolated from the internet_).
3. These control how traffic flows within your `VPC` and to and from the internet.
4. You can set up an `Internet Gateway` to allow communication between your `VPC` and the public internet.

Essentially, `VPCs` provide a secure and isolated environment for your AWS resources, giving you the flexibility to design your network architecture to meet your specific needs for security, connectivity, and scalability.

In today's project, I used `Amazon VPC` to establishing my private network space, and the `internet gateway` is a crucial component that enables internet connectivity for resources within my private space (NextWork VPC).

### How VPCs work

<img width="1376" height="768" alt="04 - architecture diagram" src="https://github.com/user-attachments/assets/caa32c5b-9be0-4fa1-9f65-df39125025c2" />

`Amazon VPC` creates a private, isolated virtual network within AWS where you can launch resources like `EC2 instances`. You control its IP address ranges, divide it into subnets _(public or private)_, and manage traffic flow with route tables and **network gateways** (like _Internet Gateways_ or _NAT Gateways_). Security is handled through `security groups` and `network ACLs`. This setup provides a secure and flexible environment for your AWS resources.

With `medium-sized VPC CIDR Block` always a /16 subnet mask that define provides range around 65,536 IP addresses.

## Subnets

### What I did in this step

<img width="924" height="859" alt="high-step2 1" src="https://github.com/user-attachments/assets/8339837c-255a-4997-bc7f-27f05c4df4dd" />

In this step, I will create `subnets` for my VPC to logically divide my network into smaller, manageable sections. This allows me to organize and isolate different resources, and effectively manage the allocation of IP addresses within my VPC.

### Creating and configuring subnets

`Subnets` are subdivision of `VPC` that contain range of ip addresses that organize group resources that need to connected to the internet `(public Subnets)` and  that won't be connected to the internet `(a private subnet)`. 

When Im create a `subnet` within my VPC, that `subnet` has to fall under a specific AZ instead of the entire Region! By spreading my resources across `multiple AZ in the same region`, that's essentially creating **backup options**. If one AZ faces issues, others can step up to keep my application running without any issues for my users.

#### Subnet Default 

<img width="1918" height="459" alt="image" src="https://github.com/user-attachments/assets/6a203587-06a5-4be0-ab13-275fb8cbf760" />

There are already subnets existing in my account, because default vpc automatically creates predefined subnets in each `Availability Zone (AZ) of a Region`.

### Public vs private subnets

The difference between public and private subnets are `internet gateway`, it has to associate an `internet gateway` with a VPC then be able to manage the route tables and route packets that needs to go to the internet with explicitly enable the `"Enable auto-assign public IPv4 address"` setting for that `subnet`. When this setting is active, So instances that are created inside that subnet will automatically have a public IP associated.

Private subnets does not have a route to an `Internet Gateway` in its route table, so the traffic in the VPC stays local, which means only connected to other Resources environment on Your AWS Account.

![Image](http://learn.nextwork.org/motivated_teal_shy_hog/uploads/aws-networks-vpc_157c4219)

### Auto-assigning public IPv4 addresses

<img width="1919" height="451" alt="image" src="https://github.com/user-attachments/assets/d596407f-3ba7-49da-998d-bbbac20c559d" />

Once I created the subnet, I enabled the `automatic assignment of public IPv4 addresses` in the `subnet settings`. This is important because `EC2 instances` need a `public IP address` to communicate with the internet or be accessible from it. By enabling this setting, any `EC2 instance` launched in this `subnet` will automatically receive a `public IP address`, which is a huge time-saver as it removes the need to manually assign one.

In this step, I am creating an `Internet Gateway` to connect my `VPC` to the internet. This allows resources within my VPC to communicate with the outside world.

### Setting up internet gateways

<img width="1903" height="707" alt="image" src="https://github.com/user-attachments/assets/1fba4075-51f7-4255-9e13-6b5a11f45878" />

`Internet Gateways` are components you create and attach to your `VPCs`. Think of them as the bridge that connects your private city `(VPC)` to the outside world (the `public internet`). They act as the connection point, allowing internet-routable traffic to __flow in__ and __out__ of your `VPC`.

<img width="1915" height="491" alt="image" src="https://github.com/user-attachments/assets/c20461a4-e912-4ccf-b5aa-7cc04637159d" />

Attaching an `internet gateway` to a `VPC` means resources in my VPC can now access the internet.

Without an `Internet Gateway` attached to `VPC`, resources within my VPC wouldn't be able to communicate with the internet, and external users wouldn't be able to access any applications host there.
