## IAM Policies

### What I did in this step

In this step, I will set up intern employee permission to the development EC2 Instance, because i'm want to ensure the intern has access to their working environment **without accidentally affecting the live production system**. This prevents them from inadvertently shutting down the platform or pushing untested changes to the production environment while they are still learning and testing.

### Understanding IAM policies

`IAM Policies` is a set of rule for who can do what with your AWS resources. It's all about `giving permissions` to IAM users, groups, or roles, saying what they can or can't do on certain resources, and when those rules kick in.

### The policy I set up

For this project, I’ve set up a policy using `JSON` to define the IAM policy that grants specific access to the development EC2 instance while restricting access to the production instance. This allows me to clearly define :  
1. `Effect` (Allow/Deny)
2. `Action` (what can be done)
3. `Resource` (what it can be done to)
4. `Condition` (when it can be done).

```JSON
{    
  "Version": "2012-10-17",    
  "Statement": [        
    {            
      "Effect": "Allow",            
      "Action": "ec2:*",            
      "Resource": "*",            
      "Condition": {                
        "StringEquals": {                    
          "ec2:ResourceTag/Env": "development"                
        }            
      }        
    },        
    {            
      "Effect": "Allow",            
      "Action": "ec2:Describe*",            
      "Resource": "*"        
    },        
    {            
      "Effect": "Deny",            
      "Action": [                
        "ec2:DeleteTags",                
        "ec2:CreateTags"            
      ],            
      "Resource": "*"        
    }    
  ] 
}

```

### Policy effect

I’ve created a policy that allows some actions (like starting, stopping, and describing EC2 instances) for instances tagged with `"Env = development"` while denying the ability to create or delete tags for all instances.

### Understanding Effect, Action, and Resource

* `Effect:` Think of this as the "yes" or "no" switch for a permission. It tells AWS whether to `Allow` (let it happen) or `Deny` (stop it from happening) a specific action. If a policy has both an `Allow` and a `Deny` for the same action, `Deny` always wins!
* `Action:` This describes exactly what someone (or something) can do. For example, `ec2:*` means "all possible actions related to EC2 instances." You can get very specific here, like `s3:GetObject` to only allow reading an object from an S3 bucket.
* `Resource:` This specifies *what* the Action applies to. If you see `*`, it means "all resources" of a certain type within the policy's scope. For example :
	> if the Action is about EC2, then `*` would mean all EC2 instances. You can also specify a very particular resource, like a single S3 bucket.

These three elements work together to form a clear rule about who can do what, and to which AWS resources!

`IAM user groups` are collection/folder of `IAM users`. It allows you to manage permissions for all the users in your group at the same time by attaching policies to the group rather than individual users.

## IAM Policy Simulator

To extend my project, I'm going to verify that the policies you create grant the intended permissions and, just as importantly, restrict unintended access with `IAM Policy Simulator`, I'm doing this because to confirm that the intern's permissions are correctly configured, allowing them access to the development environment while restricting access to production resources. It's a critical step in ensuring the security configurations are working as expected before deploying them in a real-world scenario.

### Understanding the IAM Policy Simulator

The `IAM Policy Simulator` is a special IAM tool called the Policy Simulator to validate policies without affecting your actual AWS resources. 

1. _Verify Permissions_: Ensure your policies grant exactly the access you want, no more, no less.
2. _Troubleshoot Access Issues_: If a user is having trouble accessing a resource, the simulator can help you pinpoint which policy is causing the issue.
3. _Understand Policy Logic_: It helps you see how different policy statements (Allow, Deny, conditions) interact with each other.

### How I used the simulator

I set up a simulation for tested directly in the project `(production and development instance)`, The results were denied at first, after I had to adjust the `StopInstances` arrow, and in the Instance field, add development to indicate that i want to run the simulation for the instances with that tag. the simulation results for the development instance showed that the action to stop it was successful.
